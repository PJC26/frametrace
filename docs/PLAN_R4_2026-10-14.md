# 4라운드 수정 계획 — 전체 적대적 리뷰 3차 (2026-10-14, 기준 6f227af)

리뷰 5영역 + 무결성 하위 리뷰 3건(파서·스캔·카빙 / 이어붙이기·소리·감사·서명 / 보고서·패키지·가림)의 결과 전부를 고친다. 작성: 통합자(Opus, Fable·omo 사용 불가). 구현: Opus(어려움·보통), Sonnet(테스트·문서).

## 0. 공통 규칙
- CLAUDE.md 게이트 전부 + 이 문서 §8의 추가 게이트.
- 주석(마크·메모·태그·IN/OUT) 무손실, 조용한 실패 금지, 보고서는 검증한 것만 주장.
- `state_lock` 아래에서 디스크·DB·외부 도구 작업 금지(`FRAMETRACE_DEBUG_LOCKS=1`로 확인).
- 단축키·UI 규칙 보존. 테스트는 실제 사용자 설정을 건드리지 않음. 고정 sleep 금지.
- 각 수정에는 **수정 전 코드에서 실패하는 테스트**를 붙인다(불가능하면 이유를 보고).

- 파일 소유권은 §7 표를 따른다. 남의 파일이 필요하면 "통합 TODO"로 보고(정확한 변경 내용 포함).

## §D4 as implemented (트랙 D, 2026-10-14)

### 서명 기록 스키마 v4 (`review/signoff.json`) — 정확한 형태
`crate::report::Signoff::build_v4(case_dir, examiner, signed_unix)`가 쓰는 바이트(한 줄 + `\n`, 키 순서 고정, 같은 상태·이름·시각이면 같은 바이트):
```
{"schema_version":4,"examiner":"<입력값>","signed_unix":<i64>,"content":"review marks (status, note, IN-OUT range), tags, the SHA-256 of each annotated record's target file, and the head of every audit lane","annotations_sha256":"<v3 digest>","evidence":{"<record id>":"<sha256 소문자>"|null,...},"lanes":{"<root 기준 상대경로>":{"entries":<u64>,"last_entry_sha256":"<hex>"},...},"content_sha256":"<hex>","note":"examiner name recorded as typed at finalize; not an authenticated identity"}
```
- `annotations_sha256` = `sha256(signoff_content_json_from(marks, tags))` — v3 내용(마크·메모·IN/OUT·태그) 그대로(바이트 고정, `tests_review3` 핀 유지).
- `evidence`: 마크가 있는 id ∪ 태그가 있는 id → 대상 파일 SHA-256. 출처: `db/videos.jsonl`(vid), `artifacts/carved/carve-log.jsonl`(carve id), `evidence/logs/tsk-audit.jsonl` recover-inode(`inode:<offset>:<inode>`), `artifacts/joined/join-log.jsonl`(`join:<hash16>`). 해시가 없으면 `null`. id 바이트 순.
- `lanes`: `artifacts/**`, `evidence/logs/**` 아래 이름으로 체인 레인인 파일(`audit::is_known_chain_lane`: `KNOWN_CHAIN_LANES` 또는 `*log.jsonl`/`*-audit.jsonl`) 전부의 head(항목 수·마지막 `entry_sha256`) = **잘림 탐지 앵커**. 경로 바이트 순.
- `content_sha256` = `sha256({"schema":4,"annotations_sha256":"…","evidence":{…},"lanes":{…}})` (위와 같은 직렬화).

### 서명 감사 레인 `evidence/logs/signoff-log.jsonl`
`crate::report::record_signoff_audit(case_dir, &Signoff) -> Result<(), String>`(B18이 호출)이 `append_chained_jsonl`로 추가(키 설정 시 HMAC):
```
{"schema_version":1,"event":"signoff","signed_unix":<i64>,"examiner":"…","signoff_schema_version":<u64>,"content_sha256":"…"|null,"signoff_record_sha256":"<서명 기록 파일 바이트의 sha256>"}
```
보고서·verify-package는 `report::signoff_audit_status(root, text)`로 "서명 기록이 감사 체인에 있음/없음/레인 검증 실패"를 표시.

### 검증 규칙 (`report::check_signoff(root, text, &SignoffDigests, SignoffScope)`)
- v4: ① `annotations_sha256` ≠ 현재 v3 digest → Changed(마크 변경) ② 기록된 evidence·lanes로 `content_sha256` 재계산 불일치 → Changed(서명 기록 변조) ③ evidence의 `Some(sha)`가 현재와 다르거나 사라짐 → Changed(대상 파일 교체), `null`은 "확인 불가" ④ 각 레인 앵커: 그 위치의 항목이 그대로면 통과(이후 추가는 정상), 줄어듦 → "끝부분이 삭제됨", 다른 항목 → "재작성", 파일 없음 → Changed. 패키지(`SignoffScope::Package`)에서 매니페스트에 없는 레인은 "확인 불가".
- v3 이하: 기존 의미 그대로(v3 Current/Changed, v2 LegacyBinding, 해시 없음 Unbound).
- `report::signoff_currency(text, &digests)`(package.rs가 지금 부르는 함수)는 v4에서 `annotations_sha256`만 비교 → 패키지 검사 5가 v4 기록에서도 오작동하지 않음. evidence·앵커 검사는 `cli::handlers::case::verify_package_extended`(CLI `verify-package`)가 추가로 수행.

### 산출물 이름 (D5, §8 계약)
`artifacts::artifact_file_name(kind, record_id, source_path, ext)` = `<kind>_<sanitize(record_id)>_<sha256(source path)[..8]>.<ext>` → `proxy_<id>_<hash8>.mp4`, `thumb_<id>_<hash8>.jpg`(충돌 시 `_001`…). record id = 색인 id / carve id / `inode:<off>:<inode>` / `join:<hash16>` / 모르면 `file`. 캐시 조회 `artifacts::find_existing_proxy(case_dir, selector)`는 새 이름 우선, D5 이전 이름(`<sanitize(selector)>_proxy_*`)도 찾음. 뷰어용 일치 규칙: `^proxy_<sanitizeSelector(id)>_[0-9a-f]{8}(_[0-9]{3})?\.mp4$`.

- `GET /?launch=<code>` (인증 게이트보다 먼저 처리, Host/Origin 검사는 동일):
  - 유효 → `303 See Other`, `Location: /`, `Set-Cookie: ft_token_<port>=<token>; HttpOnly; SameSite=Strict; Path=/` (코드 소모).
  - 무효/만료/재사용 + 이미 쿠키·헤더로 인증됨 → `303`, `Location: /` (쿠키 없음).
  - 그 밖 → `401` HTML("실행 링크가 만료되었거나 이미 사용되었습니다…").
  - 토큰 없는 모드 → 그냥 `303` `/`.
- 재실행(이미 떠 있는 서버 재사용): 새 프로세스가 인스턴스 파일의 토큰을 **헤더로만** 보내 새 코드를 받는다 —
  `POST /api/launch-code` (토큰 필요) → `{"ok":true,"code":"<32hex>","url":"/?launch=<code>","expires_in_secs":30}`; 토큰 없는 모드면 `{"ok":false,"error":…}`.
- WebView2 셸 등 `?token=` URL을 `serve::open_in_browser`로 넘기면 서버에 코드를 받아 `/?launch=`로 바꿔 연다(실패 시 토큰 없는 `/`).
- `?token=`(쿼리)·`X-FrameTrace-Token`·쿠키 인증은 스크립트·하네스용으로 그대로 유지.
- 뷰어·셸 JS는 주소창의 `launch` 쿼리도 `token`처럼 지운다(A 담당) — 서버는 이미 `/`로 리다이렉트하므로 보통 남지 않는다.

### `GET /api/mark-conflicts?offset=&limit=` (B3)
기본 `offset=0`, `limit=500`(1..=5000으로 고정, 잘못된 값은 기본값).
```json
{"ok":true,"count":<전체 미해결 id 수>,"offset":0,"limit":500,"next_offset":500,
 "conflicts":[{"id":"vid_…","server_revision":3,"server":{…},"queued":{"mark":…,"tags":…,"deleted":false,"base_revision":…},
               "client_id":…,"recorded_unix":…,"entries":2}]}
```
`next_offset`은 마지막 페이지에서 `null`. 순서는 처음 기록된 순서. 뷰어(A)는 `next_offset`이 `null`이 될 때까지 순회.
- 저널(`marks-pending/conflicts.jsonl`)은 id 색인(HashMap)으로 한 번에 재생, 결과는 (파일 크기, mtime) 키로 캐시 — `/api/status.mark_conflicts`(`{count, ids≤50}`)는 저널이 안 바뀌면 다시 읽지 않는다(5만 건 < 50 ms 테스트).
- 압축: `resolved` 기록 뒤 저널이 512줄 이상이고 절반 넘게 닫힌 기록이면, 열린 충돌의 줄만 남기고 나머지 줄을 원문 그대로 `marks-pending/conflicts-archive.jsonl`에 **먼저 덧붙인 뒤** 저널을 원자적으로 다시 쓴다(중간 크래시 = 보관본 중복, 손실 없음). 압축 전후 열린 집합 동일.

### `GET /api/marks-pending?offset=&limit=` (B6, 읽기 전용)
대기열(`marks-pending/*.json`, 도착 순)을 id별 **최신 값**으로 접은 결과:
```json
{"ok":true,"files":3,"count":2,"offset":0,"limit":500,"next_offset":null,"truncated":false,
 "unreadable":[{"file":"….json","error":"…"}],
 "entries":[{"id":"vid_1","mark":{…큐에 들어간 마크 원문…},"tags":[…]|null,"deleted":false,
             "base_revision":4|null,"client_id":"…","queued_file":"000…0002.json"}]}
```
삭제(`deleted_ids`)가 마지막이면 `"mark":null,"deleted":true`. 읽기 상한 64 MiB(넘으면 `truncated:true`). 열린 케이스가 없으면 `{"ok":false,…}`.

### 저장 대기·busy (B4, B7, B10, B11)
- 대기열 사용은 **보강 단계 진행 중(`enrichment` 있음) 또는 케이스 작업 실행 중**일 때만. 그 밖의 busy(재검증·고급 도구·최종화 등)에는 최대 2초 기다렸다가 직접 적용, 그래도 busy면
  `{"ok":false,"busy":true,"retry":true,"retry_after_ms":1000,"error":"…"}` (대기열에 넣지 않음 — 뷰어는 dirty 유지 후 재시도).
- busy가 풀릴 때마다(모든 BusyGuard/BusyLease) 남은 대기열을 상태 락 밖에서 반영(마크 게이트를 다른 쪽이 잡고 있으면 그쪽이 반영).
- `/api/import-marks`: 마크는 저장됐는데 make-report만 실패 → `{"ok":true,…,"report_url":null,"report_error":"…"}` + 작업 경고.
- 대기열 파일명: 디스크·프로세스 최고값보다 큰 단조 증가 번호(`{n:032}.json`), `create_new`로 선점 후 원자적 교체. 0바이트 선점 파일은 대기열로 치지 않음.
- finalize·import·케이스 작업은 busy를 잡은 뒤 바인딩된 케이스를 다시 확인, 바뀌었으면 `"작업 대상 케이스가 방금 바뀌었습니다 — …"`로 거부.

### 종료 코드 5 = 부분 결과 (B16, C7과 계약)
- 모든 CLI 자식: 종료 코드 5는 실패가 아니라 "완료, 부분 결과" — 출력은 쓰고, 작업 경고(`warnings`)에 `"<subcommand>: 부분 결과로 끝났습니다 (종료 코드 5) — …"` 추가.

### 그 밖
- B1: 인스턴스 파일로 신원이 확인된 서버만 재사용. 구조만 닮은 응답 서버는 재사용하지 않고, 건너뛴 선호 포트는 경고로 출력.
- B5: `review/*.html`·`reports/**.html`은 위치가 아니라 **내용**으로 신뢰 — `review/.generated.json`(SHA-256 목록 + 사용자별 키 `<config>/frametrace/generated-pages.key`의 HMAC)에 있는 페이지만 신뢰 헤더, 아니면 CSP sandbox(스크립트 없음, 보기 전용). 서버는 자신이 실행한 생성 단계(make-review, make-report, make-custody, package-case, deepfake-scan, qa) 성공 직후 목록을 갱신. 인라인 이벤트 핸들러가 없는 신뢰 페이지에는 `script-src 'self' 'sha256-…'`. 다른 컴퓨터(다른 키)에서 만든 케이스를 열면 경고.
- B12: 헤더 마감 10초, 같은 피어 주소의 미인증 연결 동시 16개(넘으면 즉시 503).
- B13: 모든 HTML 응답에 `Content-Security-Policy: frame-ancestors 'self'` + `X-Frame-Options: SAMEORIGIN`.
- B14: macOS `open`, 그 외 `xdg-open`을 끝까지 기다리고(좀비 없음) 실행 실패·종료 코드≠0이면 오류; `/api/open-folder`는 실패를 `{"ok":false,"error":…}`로 보고.
