## 1. U1·U2·U3 — 저장 프로토콜 v2 (`patch-v2`) 한 묶음

### 1.1 설계 원칙
1. 전송 단위 = **더티 레코드 id 집합**. 더티 id 하나당 그 레코드의 주석 전체(마크·메모·검토자·구간·태그)를 보낸다 → 서버가 "태그 없음"을 명시적으로 받는다(부수 버그 해결).
2. 동시성 단위 = **레코드 id당 revision 하나**(마크·태그·삭제를 통틀어). 서버는 `base_revision < 현재 revision`이면 그 id를 **적용하지 않고** 응답에 돌려준다. 다른 id는 적용된다(부분 적용).
3. 레거시 본문(`protocol` 없음 / `patch-v1`, schema 1·2)은 지금과 똑같이 받아들인다(충돌 검사 없음, 마지막 쓰기 승). 단 revision은 똑같이 올려 v2 클라이언트가 변경을 감지한다.
4. 서명 digest(`signoff_content_json`, SIGNOFF_CONTENT_SCHEMA 3)에 revision을 **넣지 않는다** → 기존 sign-off의 Current/Changed 판정 불변.
5. 대기열(`marks-pending/`)·busy 경로·`make-report` 갱신 흐름은 그대로 두되, 청크 묶음당 1회로 줄인다.

### 1.2 스키마 v7 (`src/case_db/core.rs`)
```sql
CREATE TABLE IF NOT EXISTS review_annotation_rev (
  record_id    TEXT PRIMARY KEY,
  revision     INTEGER NOT NULL,
  updated_unix INTEGER NOT NULL,
  actor        TEXT,
  client_id    TEXT            -- v2 writer token; 레거시/CLI는 NULL
);
```
- `migrate_v6_to_v7`: `backup_database("6","7")` → 표 생성 → `INSERT ... SELECT record_id, 1, marked_unix FROM review_marks` + `review_tags.v1:*` 키의 id 중 마크 없는 것도 revision 1로 → `schema_version='7'`. `review_marks`·`schema_meta` 태그·`review_mark_history`는 **한 바이트도 건드리지 않는다**(순수 추가). `Some("6") => migrate_v6_to_v7`, `Some(SCHEMA_VERSION)` 분기에 `apply_schema_v7_rev` 추가(멱등). 기존 `migrate_v5_to_v6` 등은 체인 끝을 v7로.
- 마크 무손실 보장: 마이그레이션 테스트가 v6 픽스처(마크 3·태그 2·이력 5행)에 대해 `load_review_marks`·`load_review_tags`·`load_review_mark_history` 결과가 전후 동일함을 단언하고 백업 파일 존재를 확인. `review_mark_history`는 트리거로 UPDATE/DELETE가 막혀 있어 마이그레이션이 이력을 건드릴 수 없다.
- 읽기 전용 열기(verify-package가 옛 패키지 DB를 읽음): `load_review_revisions_from(conn)`은 표가 없으면 빈 맵을 돌려준다.
- 삭제(tombstone)된 마크의 rev 행은 **남긴다** → 오래된 창이 삭제된 마크를 되살리려 해도 충돌로 잡힌다.

### 1.3 서버 쓰기 (`src/case_db/marks.rs`)
`patch_review_annotations_by`를 `patch_review_annotations_v2(case_dir, patch: &AnnotationPatch, actor, client_id) -> PatchOutcome`로 확장(기존 시그니처는 v2를 `base=None`으로 호출하는 얇은 래퍼로 유지).
- 트랜잭션 하나(BEGIN IMMEDIATE). id별로: `current = rev 행 또는 0`. v2이고 `base_revision(없으면 0) < current` → **건너뛰고** `conflicts.push({id, server_revision, server: {status, marked_unix, examiner, note, range, tags} | null})`. 아니면 지금 로직대로 삭제/태그/upsert 수행 → 효과적 변경(old != new)이 하나라도 있으면 `revision += 1, updated_unix = now, actor, client_id` 기록. 변경 없으면 rev 불변(재전송 멱등).
- 이력 행 `detail`에 `client:<client_id>`를 적는다(어느 창이 썼는지 감사).
- v2에서 더티 id의 `tags`는 항상 명시(빈 배열 = 삭제). `deleted_ids`는 "마크 삭제"로 유지하되 v2에서는 그 id의 `tags`도 동봉된다.
- 반환: `PatchOutcome { applied: Vec<(id, revision)>, conflicts: Vec<Conflict>, stored: usize }`.

### 1.4 요청·응답 형식 (`src/selection.rs` parse_marks_text 확장)
요청(더티 id만, 청크 하나):
```json
{ "schema_version": 2, "protocol": "patch-v2", "case_id": "...", "examiner": "kim",
  "client_id": "w-7f3a…", "exported_unix": 1760000000,
  "batch": { "id": "b-01J…", "index": 0, "total": 3 },
  "base_revisions": { "vid_000001": 4, "vid_000009": 0 },
  "marks": [ { "id": "vid_000001", "status": "important", "marked_unix": …, "note": "…", "examiner": "kim", "range": {"in": 1.5, "out": 4.0}, "tags": ["사고"] } ],
  "tags":  [ { "id": "vid_000009", "tags": [] } ],
  "deleted_ids": ["vid_000009"] }
```
- 파서: `protocol ∈ {absent, "patch-v1", "patch-v2"}` 외 거부(현행). v2이면 `base_revisions`(객체, 값 u64)·`client_id`(문자열)·`batch`(index<total) 검증. `MarksFile`에 `base_revisions: Option<BTreeMap<String,u64>>`, `client_id`, `batch` 추가. 마크 항목의 `tags`는 v2에서만 읽고 `tags` 배열과 합쳐 id당 하나로 정규화(중복 id는 거부).
- 응답(`api_import_marks`):
```json
{ "ok": true, "protocol": "patch-v2", "stored": 12, "applied": { "vid_000001": 5 },
  "conflicts": [ { "id": "vid_000002", "server_revision": 3, "server": { "status": "reviewed", "note": "", "examiner": "lee", "range": null, "tags": ["보류"] } } ],
  "batch_done": true, "deferred": false, "report_url": "case/reports/case-report.html" }
```
  `deferred:true`면 `pending`만 추가(현행). 413은 지금처럼 JSON 오류지만 클라이언트가 구분해 처리(1.6).

### 1.5 서버 경로 (`src/serve/jobs.rs` api_import_marks / import_marks_during_enrichment / drain_pending_marks)
- 본문 파싱·케이스 바인딩 검사 그대로. busy 경로: 자식 프로세스 `import-marks`를 거치면 충돌 목록을 돌려줄 수 없으므로 **in-process** `import_marks_quiet`(이미 존재)로 바꾸고 결과를 응답에 싣는다. `make-report` 자식 실행은 `batch`가 없거나 `index == total-1`일 때만(청크 묶음당 1회). 청크 중간 실패 시 다음 청크는 클라이언트가 재시도하므로 서버는 청크를 독립 트랜잭션으로 둔다(id별 revision 멱등이라 재전송 안전).

- `/api/records-meta`와 make-review의 `annotations` JSON에 `"revisions": {id: n}` 맵 추가(`src/case_db/evidence.rs`에 `review_annotations_json(case_dir)` 신설, 호출부 2곳: `serve/records.rs`, `cli/handlers/case.rs` make_review).

### 1.6 클라이언트 (`assets/viewer/90-sync.js`, `30-records.js`, `80-review.js`, `65-actions.js`)
**상태 구조**
- `state.deletedIds: string[]` → `state.dirty: Set<string>`(이름은 `dirtyIds`로, 90-sync/30-records/00-host summary/`scripts/verify-review-batch.mjs` 단위 모드의 참조 전부 교체). `touchAnnotation`은 `dirtyIds.add(id)`만(O(1)).
- `state.revisions: {id: n}` — `DATA.annotations.revisions`에서 시드, 응답 `applied`로 갱신.
- drafts 항목: `{ mark, note, tags, examiner, range, seq, writer }`. `seq`는 창 단위 증가 카운터, `writer`는 `FTViewer.writerToken`.

**드래프트 저장(증분·디바운스)**
- `touchAnnotation`은 메모리만 바꾸고 `scheduleDraftFlush()`(250 ms 디바운스, `requestIdleCallback` 폴백 setTimeout)로 **한 번에** `ANNOTATIONS_KEY`를 쓴다. `applyMarkJournaled`/`markActive`/`applyTag`/`clearTags`/노트 입력의 `storageSet(MARKS_KEY|TAGS_KEY|NOTES_KEY)` 호출은 **서버 모드에서 제거**(hydrate가 덮어쓰므로 효과 없음; standalone 모드는 drafts만으로도 복원되는지 `verify-viewer-undo`로 확인 후 동일 처리). `RANGES_KEY`는 서버 시드가 필요하므로 flush에 합류.
- 쿼터: `storageSet`(정의 위치 10-boot.js 추정)이 `QuotaExceededError`를 잡으면 세션당 토스트 1회 + `saveState` title에 사유, 이후 flush는 조용히 건너뛰고 `draftsUnpersisted=true`로 `beforeunload` 경고만 유지.
- `beforeunload` 직전 `flushDraftsNow()`.

**페이로드·청크**
- `marksPayload()` = `dirtyIds`만. 각 id에 현재 마크(없으면 `deleted_ids`)·메모·검토자·구간(충돌 보류 id는 현행대로 생략)·`tags`(항상)·`base_revisions[id] = state.revisions[id] ?? 0`.
- `splitPayloadChunks(payload, {maxIds: 2000, maxBytes: 1 MiB})` → 순차 POST(`batch.index/total`, 같은 `batch.id`). 청크 하나가 413이면 `maxIds`를 반으로 줄여 그 청크부터 재시도(하한 50, 그 아래면 실패 표시). 전송 중 들어온 편집은 `saveRevision` 비교 그대로(다음 라운드).
- 성공 처리: `applied`의 id만 `dirtyIds`에서 제거하고 drafts에서 **그 id만, 전송 시 `seq`와 같을 때만** 삭제(다른 창·전송 중 편집 보존). `clearReviewDirty()` 전체 삭제는 폐지.

**충돌 UI**
- `conflicts`의 id는 `dirtyIds`에서 빼고 `conflictIds: Map<id, {server, server_revision, mine}>`에 넣는다. 기존 `rangeDivergenceBanner`와 같은 패턴의 배너 `#markConflictBanner`(role=alert, 버튼 2개): **[서버 값 사용]** = 서버 값으로 state·drafts 교체, `revisions[id]=server_revision`; **[내 값으로 덮어쓰기]** = `revisions[id]=server_revision` 후 `touchAnnotation(id)` → 다음 저장에서 적용. 항목별 보기는 title 툴팁(≤20건)으로 현행 패턴 유지. i18n 키 `conflict.msg/useServer/useMine`(`20-i18n.js`).
- `pendingSaveCount()`에 `conflictIds.size`를 포함 → `saveState`는 `pending`으로 남고(enum 불변), 최종화의 "미저장 마크 차단"이 그대로 작동. `save-state` 이벤트 detail에 `conflicts` 수 추가(기존 소비자는 무시).
- 대기열 충돌: `watchServerQueue()`가 `/api/status.mark_conflicts.count > 0`이면 `/api/records-meta` annotations를 받아 해당 id의 서버 값과 revision으로 같은 배너를 띄운다.

**두 창 보호(U2 잔여)**
- 하트비트 키 `ft.alive:<case>:<writer>`를 5 s마다 갱신. 부팅 hydrate는 drafts 중 `writer == 나` 또는 하트비트가 30 s 이상 오래된 writer의 것만 흡수(크래시 복구), 살아 있는 다른 창의 drafts는 건드리지 않는다. 살아 있는 다른 writer가 있으면 세션당 1회 토스트 "같은 케이스가 다른 창에서도 열려 있습니다 — 충돌 시 알려 드립니다".

### 2.1 동작 (`src/case_merge.rs` + 신규 `src/case_db/merge_annotations.rs`)

## 7. 적대적 리뷰 포인트
1. 충돌 검사 우회: v2 본문에서 `base_revisions`를 통째로 빼면 모두 0 → 서버에 rev>0인 id가 있으면 전부 충돌로 잡히는가(덮어쓰기가 아니라).
2. 삭제 → 다른 창의 재생성: tombstone rev 행이 남아 충돌로 잡히는가. 반대로 같은 창의 삭제→재생성은 자기 revision으로 통과하는가.
3. 청크 중간 실패/413 반감 후 재전송 시 중복 이력 행이 생기지 않는가(멱등).
4. 대기열 드레인 충돌이 `conflicts.jsonl`에 **원문 전체**를 남기는가(마크 손실 0). 서버 재시작 후에도 `/api/status.mark_conflicts`가 보이는가.
5. drafts 부분 삭제: 전송 중 편집한 id의 draft가 남는가(`seq` 비교). 하트비트 30 s 규칙이 절전/탭 슬립에서 살아 있는 창의 draft를 "고아"로 잘못 흡수하지 않는가(탭 복귀 시 즉시 하트비트).
6. `pendingSaveCount`에 충돌을 포함했을 때 최종화 사전 점검이 차단되는가; "서버 값 사용"으로 해소하면 즉시 saved가 되는가.
7. 서버 모드에서 MARKS/NOTES/TAGS 맵 쓰기를 뺀 뒤 standalone(file://) 뷰어의 drafts 복원·Undo가 그대로인가(`verify-viewer-undo`, `verify-range-sync`).
8. 레거시 digest: `review_marks_json_from_rows` 문자열이 바이트 동일한지 핀 테스트가 실제로 옛 픽스처를 쓰는가. 옛 sign-off 패키지가 verify-package에서 여전히 PASS인가.
9. 병합 메모 접두 `[병합 …]`가 두 번째 병합에서 중복되지 않는가; 메모가 `\n`을 포함할 때 보고서·CSV에서 깨지지 않는가.
10. 병합 트랜잭션 롤백이 `review_annotation_rev`까지 포함하는가; 소스 케이스가 v5(이력 표 없음)일 때 빈 이력으로 정상 진행하는가.
11. 패키지: `review/data-bundle.js`에 절대 경로가 들어가는데 `--redact-paths`(I4, 범위 밖)와 상호작용을 README/문서에 명시했는가.
12. 보고서 "판독" 열의 태그·구간 이스케이프; `range.in`만 있는 경우 표시.
13. `make-report`를 마지막 청크에서만 돌리는 변경이 단일 요청(배치 없음) 경로를 깨지 않는가; 레거시 클라이언트는 매번 돌아가는가.

## 9. Track A contract as implemented (2026-10-13, 서버 측 — 트랙 B는 이 절에 맞춘다)

§1.2~§1.5를 그대로 구현했다. §0/§8의 "추정"은 이렇게 확인했다: `api_status`는 `src/serve/system.rs`에 있다(맞음). `/api/records-meta`의 `annotations`는 `{marks:[ReviewMarkRow…], tags:[{id,tags}…]}`였고 여기에 `revisions`를 더했다. **케이스 DB는 WAL이 아니다**(rollback journal; `records.rs`의 `-wal` stamp는 방어 코드). 해시 단계의 긴 쓰기 트랜잭션 중에도 revision 읽기는 되고, 커밋 순간만 `busy_timeout` 5 s 안에서 기다린다.

### 9.1 요청 (`POST /api/import-marks`, 본문 `{"marks_json": "<아래 JSON 문자열>"}`)
§1.4와 동일. 파서(`src/selection.rs` `parse_marks_text`)의 규칙:
- `protocol`: 없음(레거시 전체 내보내기) · `"patch-v1"` · `"patch-v2"`. 그 외 → `{"ok":false,"error":"unsupported marks protocol"}`.
- `schema_version`: 1 또는 2(현행 그대로; v2도 2를 보낸다).
- **patch-v2 전용 필드**(레거시/v1 본문에서는 값이 이상해도 무시):
  - `base_revisions`: `{id: u64}` 객체. **없거나 null이면 빈 맵** = 모든 id의 base 0 → 서버 revision ≥ 1인 id는 전부 충돌(덮어쓰기 아님, §7.1). 음수·소수·문자열 값, 객체가 아닌 값은 거부.
  - `client_id`: 문자열(빈 문자열 거부). 생략 가능. 이력 행 `detail`에 `client:<client_id>`, `review_annotation_rev.client_id`에 그대로 기록.
  - `batch`: `{id: 비어 있지 않은 문자열, index: u64, total: u64 ≥ 1}`, `index < total`. 생략 = 단일 요청. 객체가 아니면 거부.
  - 마크 항목의 `tags` 배열은 **v2에서만** 읽어 `tags` 목록과 합쳐 id당 하나로 정규화. 같은 id가 양쪽에 있으면 거부(`both inline`). v1/레거시는 마크 안 `tags`를 지금처럼 무시.
  - `deleted_ids`는 v1·v2에서 허용(레거시에서는 거부, 현행).
- 서버는 "더티 id마다 `tags`를 반드시 보내라"를 **강제하지 않는다**: `tags` 항목이 없는 id는 태그를 건드리지 않는다. 빈 배열 `[]`만이 "태그 전부 삭제"다(마크 없는 레코드도 같음).
- 본문 4 MiB(`MAX_BODY`) 초과 → **HTTP 413, 본문은 `request body too large` 평문**(JSON 아님 — `src/serve/http.rs`는 트랙 A 소유가 아니라 바꾸지 않았다; §1.4의 "JSON 오류"는 틀린 서술). 클라이언트는 상태 코드로 분기한다.

```json
                               "range": {"in": 1.0, "out": 2.0}, "tags": ["보류"] } } ],
  "batch_done": true,
  "deferred": false,
  "report_url": "case/reports/case-report.html" }
```
- `protocol`: 요청의 값을 그대로(레거시 = `null`). `stored`: 실제 upsert된 마크 행 수(충돌 id 제외).
- `applied`: 충돌이 아닌 **모든** id → 패치 후 revision. 값은 **항상 숫자**(옛 `applied:true` 불리언 폐지). 변경 없는 재전송은 같은 revision으로 돌아온다(멱등, 이력 행 없음). 더티 id를 지우는 기준은 `applied`에 있는 id뿐.
- `conflicts[].server`: 서버에 마크도 태그도 없으면(삭제 tombstone) `null`. 태그만 있으면 `status`·`marked_unix`·`examiner`·`note`·`range`가 `null`, `tags`만 참. `range`는 저장된 IN/OUT이 하나라도 있을 때만 객체, 아니면 `null`.
- `batch_done`: `batch` 없음 또는 `index == total-1`. `report_url`: make-report가 실제로 돈 요청에만 문자열, 그 외 `null`.
- `deferred: true` 응답: `{ok:true, protocol, stored:0, applied:{}, conflicts:[], batch_done, deferred:true, pending:n, report_url:null}`. 대기열 본문은 드레인 때 적용되고, 그때의 충돌은 9.4로 간다. `deferred` 키는 모든 성공 응답에 있다(`false` 포함).
- 레거시/v1 본문: `conflicts`는 항상 `[]`(마지막 쓰기 승)이지만 `applied`에는 올라간 revision이 들어온다. make-report는 요청마다(`batch` 없음).
- 실패는 현행대로 `{"ok":false,"error":"…"}`. 충돌은 실패가 아니다(`ok:true`).
- 청크마다 독립 트랜잭션. make-report(자식 프로세스)는 `batch`가 없거나 마지막 청크일 때 **1회**. 중간 청크 실패 후 재전송은 id별 revision 검사로 멱등.
- enrichment(review-partial) 중 직접 적용 경로도 같은 모양이며 make-report는 돌지 않는다(`report_url:null`; 리뷰 재생성이 포함).

### 9.3 `/api/records-meta` · make-review `annotations`
```json
"annotations": { "marks": [ReviewMarkRow…], "tags": [{"id","tags"}…], "revisions": { "vid_000001": 5 } }
```
두 곳 모두 `case_db::evidence::review_annotations_value / review_annotations_json(case_dir)`가 만든다(호출부: `serve/records.rs`, `cli/handlers/case.rs` make_review — 후자는 트랙 A가 그 한 줄만 바꿨다). 읽기 실패는 records-meta에서는 `annotations.error` 문자열(+빈 목록)로 보이고, make-review는 오류로 중단한다(이전엔 조용히 빈 목록). revision 표가 없는 옛 DB(verify-package 등)는 `revisions: {}`.

### 9.4 대기열 충돌 저널과 `/api/status.mark_conflicts`
- 파일 `marks-pending/conflicts.jsonl`(append-only; 서버 재시작 후에도 읽음). 드레인 중 충돌 1건당 1줄:
  ```json
  {"recorded_unix":…, "source":"<대기열 파일명>", "id":"vid_1", "server_revision":3, "server":{…}|null,
   "mine":{"mark":{원문 마크 항목}|null, "tags":[…]|null, "deleted":false, "base_revision":0|null},
   "client_id":"w-…"|null, "examiner":"kim"|null}
  ```
  원문 항목은 대기열 본문에서 그대로 복사한다(마크 손실 0). 저널은 대기열 파일 삭제 **전**에 fsync된다.
- 해소: 그 id가 이후 어떤 패치에서든 **적용**되면(현재 revision을 base로 보낸 저장 — 변경 없는 재전송 포함) `{"resolved":"vid_1","revision":n,"unix":…}` 줄을 덧붙인다. 원 충돌 줄은 지우지 않는다. **트랙 B 주의(§1.6에 없던 추가 규칙)**: 배너의 [서버 값 사용]도 그 id를 서버 값·`server_revision`으로 `touchAnnotation`해 한 번 저장해야 status 카운트가 내려간다.
- `/api/status`: `"mark_conflicts": {"count": <미해소 id 수(중복 제거)>, "ids": [처음 50개]}`. 케이스 없음/저널 없음 → `{"count":0,"ids":[]}`. 새 라우트 없음.
- 드레인 로그: `대기열 반영 중 충돌 n건 — 뷰어에서 확인하십시오 (marks-pending/conflicts.jsonl).`

## §10 R1 적대적 리뷰 후속 계약 (2026-10-13, 통합자 결정)

R1 적대적 리뷰(서버 13건·뷰어 15건)의 공통 원인: 충돌 검사가 "같은 창의 연속 편집"과 "내용이 같은 재전송"까지 충돌로 보고, 반대로 드래프트·리비전 갱신 경로에서는 검사를 우회한다. 아래 계약으로 서버·뷰어를 함께 고친다.

### 10.1 서버 규칙 (marks.rs patch v2)
1. **충돌 조건은 `base != current`** (base > current도 충돌 — DB 복원 대비).
2. **같은 창 예외**: `base != current`라도 rev 행의 `client_id`가 요청 `client_id`와 같고(둘 다 non-null) → 적용. (그 창이 마지막 작성자 = 자기 연속 편집, 대기열 연쇄 포함.)
3. **무변경 예외**: 충돌 조건이어도 패치 내용(상태·메모·검토자·구간·태그·삭제)이 저장된 값과 같으면 → `applied[id] = current`(리비전·이력 불변). 응답 유실 재전송·대기열 재반입이 멱등.
4. `noted` 행의 `marked_unix`는 요청 값이 아니라 기존 값을 유지하는 것으로 비교(무변경 판정에서 marked_unix 제외는 상태가 같을 때만).

### 10.2 서버 API
- `/api/records-meta` `annotations.writers: {id: client_id|null}` 추가(마지막 작성 창).
- 신규 `GET /api/mark-conflicts` → `{ok, count, conflicts:[{id, server_revision, server:{...}|null, queued:{제출된 원 항목}, client_id, recorded_unix}]}` — 미해결 전체(상한 없음). `/api/status.mark_conflicts`는 `{count, ids≤50}` 유지.
- 대기열 충돌 해소 조건: v2 패치가 그 id를 **적용**했고 그 패치의 `base_revision >= 기록된 server_revision`일 때만(충돌을 본 창의 결정). 레거시·v1 본문은 해소하지 않음.
- **최종화 차단**: 미해결 대기열 충돌 > 0이면 `/api/finalize`가 거부(한국어 오류: "저장 충돌 N건을 먼저 해결하십시오").
- **최종화 시 make-review 재실행** 후 패키지 → `review/data-bundle.js`가 서명된 DB와 일치.
- verify-package 검사 6: 뷰어만 있고 data-bundle 없음 → **NOT VERIFIED**(FAIL 아님, 옛 패키지 호환). package-case의 거부는 유지.
- merge: 출처 경로는 `\?\` 제거한 표시 경로, 메모 덧붙임 중복 판정은 줄 단위 정확 일치.

### 10.3 뷰어 규칙
- 드래프트는 **id별 저장 키** `ft.draft.<case>.<writer>.<id>` = `{mark,note,tags,examiner,range,seq,base,conflict?}`. 쓰기 O(1), 다른 창 키는 건드리지 않음. 기존 단일 키 드래프트는 부팅 시 1회 이관.
- 드래프트에 **base 리비전 저장**; 채택된 드래프트는 저장된 base로 전송 → 다른 창 저장 이후라면 서버가 충돌로 돌려줌(덮어쓰기 없음). 충돌 상태도 드래프트에 저장 → 리로드 후 배너 복원.
- 죽은 창 판정: 하트비트 5분 이상 + 같은 출처 BroadcastChannel ping 무응답일 때만 자동 채택. (base 저장으로 오판해도 덮어쓰기 대신 충돌.)
- 대기열 응답(deferred): 해당 id에 `queued` 표시, 드레인 후 `/api/records-meta`의 `revisions`+`writers`로: writer==나 → 리비전만 갱신; 아니고 내 더티 없음 → 값+리비전 갱신; 더티 있음 → 충돌 등록. **값 없이 리비전만 일괄 갱신 금지.**
- 대기열 충돌은 `GET /api/mark-conflicts`의 `queued`(원래 제출 값)를 "내 값"으로 표시. 충돌을 다 불러오기 전에는 `saved`를 내보내지 않음(await).
- 충돌 UI: 배너 + **건별 목록 패널**(키보드 접근, 각 건에 두 값 표시, 건별/전체 [서버 값]/[내 값] 버튼), 두 테마 AA 대비(하드코딩 색 금지, 토큰 사용; range 배너도 동일 수정).
- 충돌 해결한 id의 Undo/Redo 저널 항목은 폐기.
- 호스트 뷰어 언마운트 전에 진행 중 저장을 기다림(`22-viewer-host.js`), 중단 후 도착한 성공 응답도 드래프트 정리 반영.
- 서버 모드에서 MARKS/NOTES/TAGS 전체 맵 쓰기 제거(`60-details.js`, `50-tags.js` 포함). 대량 더티 표시는 render 1회로 묶기.
- `saveLegacyProtocol` 전환은 정확한 오류 문자열 일치일 때만.
- 셸 최종화 체크리스트(`41-finalize.js`)가 `status.mark_conflicts.count`를 차단 항목으로 표시.

### §10.4 as implemented (2026-10-13, 서버 측)

**10.1 규칙 (`src/case_db/marks.rs` `patch_review_annotations_v2`)** — id마다 순서대로:
1. `base == current` → 적용.
2. `base != current`(큰 쪽·작은 쪽 모두, rev 행이 없으면 current 0)이고 rev 행 `client_id`가 요청 `client_id`와 같으면(둘 다 non-null, 빈 문자열은 null 취급) → 적용(같은 창 연속 편집·대기열 연쇄).
3. 아니면 **무변경 판정**: 이 id의 삭제·태그·마크를 적용했을 때 저장 값(상태·메모·검토자·구간·record_path·태그·존재 여부)이 그대로면 → `applied[id] = current`, 리비전·이력·rev 행의 작성 창 모두 불변. 상태가 같으면 `marked_unix`는 비교하지 않는다.
4. 그 외 → `conflicts[]`.
- `noted` → `noted` 쓰기는 저장된 `marked_unix`를 유지한다(레거시/v1/CLI 포함 모든 경로; 재스탬프만 다른 재전송은 변경 아님 → 이력·리비전 불변).
- 요청 `client_id`가 null이면 2번 예외 없음(레거시 작성자 null끼리도 같은 창 아님).

**`/api/records-meta` `annotations`** (make-review 번들에는 `writers` 없음 — 서명 패키지에 창 토큰을 넣지 않는다):
```json
"annotations": {
  "marks": [ReviewMarkRow…],
  "tags": [{"id": "vid_1", "tags": ["사고"]}],
  "revisions": {"vid_1": 3, "vid_9": 1},
  "writers": {"vid_1": "w-a", "vid_9": null}
}
```
`writers[id]` = 그 id의 현재 리비전을 쓴 창의 `client_id`(레거시·v1·CLI·merge 작성은 `null`). `revisions`와 같은 키 집합이며, 마크·태그·리비전·작성 창은 **한 읽기 트랜잭션**에서 읽는다. 읽기 실패 시 `{"marks":[],"tags":[],"revisions":{},"writers":{},"error":"…"}`.

**`GET /api/mark-conflicts`** (다른 API GET과 같은 인증 등급: 토큰 설정 시 Token, 아니면 공개 읽기. 케이스 없음 → `count:0`):
```json
{ "ok": true,
  "count": 1,
  "conflicts": [
    { "id": "vid_1",
      "server_revision": 1,
      "server": { "status": "reviewed", "marked_unix": 50, "examiner": "lee", "note": "server",
                  "range": null, "tags": [] },
      "queued": { "mark": { "id": "vid_1", "status": "important", "marked_unix": 100, "note": "mine",
                            "examiner": "kim", "range": {"in": 1.0, "out": 2.0}, "tags": ["사고"] },
                  "tags": null, "deleted": false, "base_revision": 0 },
      "client_id": "w-a",
      "recorded_unix": 1760000000,
      "entries": 1 } ] }
```
- id당 1건(첫 기록 순서), 상한 없음. `count`는 `/api/status.mark_conflicts.count`와 같다(id 수).
- `server`·`queued`·`client_id`·`recorded_unix`는 그 id의 **가장 최근** 미해결 저널 줄에서 온다. `queued`는 저널의 `mine`을 그대로(`mark`/`tags`는 대기열 본문 원문 항목, 없으면 `null`; 서버 값이 없으면 `server: null`).
- `server_revision`은 그 id의 미해결 줄들 중 **최댓값**(해소에 필요한 최소 base). `entries` = 그 id의 미해결 줄 수(같은 id가 대기열 본문 여러 개에서 충돌한 경우 > 1; 이전 줄은 `marks-pending/conflicts.jsonl`에 남아 있다).

**해소 규칙**: patch-v2 본문이 그 id를 `applied`에 넣었고 그 본문의 `base_revisions[id]`(없으면 0) ≥ 위 `server_revision`일 때만 `{"resolved":id,"revision":n,"unix":t}` 줄을 덧붙인다. 레거시·patch-v1 본문, 무변경 예외로 오래된 base와 함께 적용된 저장, 같은 창 예외로 오래된 base와 함께 적용된 저장은 해소하지 않는다. 직접 저장·enrichment 중 직접 적용·대기열 드레인 세 경로 모두 같다(드레인은 대기열 파일을 다시 파싱해 base를 얻는다).

**최종화** (`finalize_with_exe`): 대기열 드레인 → 미해결 충돌 > 0이면 거부 `{"ok":false,"error":"최종화 차단: 저장 충돌 N건을 먼저 해결하십시오 (뷰어의 충돌 목록에서 서버 값 또는 내 값을 선택해 저장)."}`(서명 파일 없음) → **`make-review <case>`** (실패 시 거부, phase `review-ready`) → 서명(pending) → `make-report --rehash --signoff` → `package-case` → 서명 확정. CLI에는 최종화 명령이 없어 서버 경로만 바뀌었다; `package-case` 자체는 그대로(뷰어만 있고 번들 없으면 거부).

**verify-package 검사 6**: 뷰어만 있고 `review/data-bundle.js`가 없으면 `NOT VERIFIED`(이전 FAIL). `package-case`의 거부는 유지.

**merge-cases**: 원본 케이스 경로는 `canonicalize` 후 `util::strip_windows_extended_prefix`를 거친 표시 경로로 `merged_from`·`merge_provenance[].source_case`·감사 로그 `source_case`·이력 `detail`·메모 덧붙임 접두 `[병합 <경로> <id>]`에 기록(읽기는 정규 경로로). 메모 덧붙임 중복 판정은 부분 문자열이 아니라 **연속된 줄 단위 정확 일치**(덧붙일 조각의 줄들이 기존 메모의 연속된 줄들과 정확히 같을 때만 생략).

**마이그레이션 백업**: 체인(v1~v6 → v7)마다 **한 번**, `BEGIN IMMEDIATE` 전에 SQLite 온라인 백업 API로 `case.db.backup-v<원래 버전>-to-v7-<unix>`를 만든다(이전: 단계마다 트랜잭션 도중 `fs::copy` → v2-to-v3 등 이름이 실제 내용과 다르고 찢어질 수 있었음). 잠금 아래에서 다시 읽은 버전이 백업한 버전과 다르면 마이그레이션하지 않고 오류. 백업 이름 테스트는 `-to-v7-` 접두로 바꿨다(`docs/schema.md`의 옛 이름 예시는 손대지 않았다).
