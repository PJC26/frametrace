## 0. 원칙 확장
R11의 P9는 "사용 불가 줄의 **내용**"(event·run_id)을 판정에 썼기 때문에 꼬리 줄 하나를 고쳐 우회됐다. S3의 순서 변경은 승격과 패키징 사이의 중단·크래시 창을 디스크에 남기지 않았다.

> **P12. 사용 불가 줄의 내용은 판정에 쓰지 않는다 — 위치만 쓴다.** 결과 실행의 완료 표식 뒤에 사용 불가 줄이 하나라도 있으면(event·파싱 여부 무관) 결과는 보류(withheld)이고 그 수는 `unauthenticated`에 들어간다.
> **P13. 최종화는 디스크 저널로 재개 가능해야 한다.** 승격 전에 `review/finalize.inprogress.json`(서명 SHA, 이전 서명 바이트)을 fsync로 쓰고, 성공 시 지운다. 서버 시작·케이스 열기 때 남아 있으면 포기 기록·복원·보고서 재생성을 수행하거나 status에 표시한다. 정리 단계는 취소 불가다.
> **P14. 게시된 패키지는 반드시 서버가 안다.** 패키지 단계는 게시 rename 뒤 취소를 받지 않고, 성공 종료 코드가 관찰되면 cancel을 무시한다. 실패 경로는 stdout `output:`·reports 새 폴더로 게시 여부를 확인해 `_INCOMPLETE` 표식을 다시 적용한다.

공통 규칙은 `PLAN_R4_2026-10-14.md` §0.

### 트랙 U 계약
- **`/api/status` 새 필드**:
  - `finalize_recovered: bool`, `finalize_recovered_detail: string|null` — 이 서버가 중단된 최종화를 복구했음(시작·케이스 열기·다음 최종화 시). detail은 한 일과 "확인 필요: …"(남은 것). 최종화 성공·다른 케이스로 초기화. 표시: "이전 최종화 중단됨 — 복구됨"(+detail).
  - `finalize_journal: null | {path, state, examiner, started_unix, signoff_sha256, error}` — 디스크에 저널이 남아 있음. **이 서버 자신의 최종화가 진행 중(`phase:"finalizing"`)이면 `null`**. `state`: `"recovered"`(보고서 재생성만 남음 — 다음 최종화가 처리) / `"interrupted"`(되돌리기·abandon·표식 중 실패 — 확인 필요) / `"in-progress"`(아직 복구 안 됨: 다른 살아 있는 FrameTrace가 쓰는 중 등) / `"unreadable"`(파일 손상, `error`에 이유; 다음 최종화 차단). 뷰어 규칙(조정자 요청과 동일): `state !== "recovered"` → "이전 최종화 중단됨 — 확인 필요", `finalize_recovered` 또는 `state === "recovered"` → "복구됨".
  - 기존 `report_stale`은 복구가 보고서 marker = 중단된 서명이라고 판정하면 true.
- **`POST /api/finalize` 실패**: 새 필드 `incomplete_package_dirs: string[]`(이번 최종화가 게시·보존한 패키지, 이제 `…_INCOMPLETE` 또는 옆 표식). `error`에 "이번 최종화의 패키지는 이미 …에 만들어졌지만 최종화는 끝나지 않았습니다 — 폴더 이름을 …로 바꿨고 옆에 표식 …"이 붙음. 이전 저널을 정리하지 못하면 "최종화 차단: 이전에 중단된 최종화를 정리하지 못했습니다 — …". 포기된 이전 서명: "…되돌리지 않았습니다 — 지금 확정된 검토자 기록이 없습니다".
- **`POST /api/finalize` 성공**: 변화 없음. 게시 뒤 cancel은 무시되고 로그 "중단 요청을 받았지만 패키지가 이미 게시되어 …". 즉 "작업 중단 후 서버 종료"는 게시 후엔 패키지 단계가 끝난 뒤(보통 수 초) 종료.
- **`verify-package --strict`**: 3 = 미완료 최종화 **또는 서명 NOT VERIFIED**(서명 없음, 체인 확인 불가 — 다른 PC 키 등). 1 = FAIL, 0 = 그 외.
